# Проверка интеграции Laya: новая сессия, A/B/C, доставка DoneGate

Дата: 2026-11-02. Модель CLI: `Kibborg_Flash_v5.7` (`new-provider`), одинаковая
для всех прогонов. Репозиторий-фикстура: `<bench-root>\template`
(один коммит, один и тот же баг). Все прогоны — `--mode yolo`, `--json`.

## 1. Новая сессия видит 13 инструментов

Сессия `sess_c68e0042-1e31-4794-8047-bc58995ca519` (headless, новый процесс)
перечислила точные имена 13 `laya_*` MCP-инструментов и реально вызвала
`laya_health` и `laya_search`:

- `laya_health`: `cuda`, checkpoint `multilingual-fp16-0b095e005a4c`, 12 мс;
- `laya_search`: 6 совпадений, Laya отранжировала 6 кандидатов, 403 мс;
- usage этой сессии: **395 628 input**, **629 output**, **262 104 cache read**,
  3 model requests.

То есть инструменты не только зарегистрированы, но и доступны основной модели
и вызываются ею.

## 2. A/B/C на одинаковой задаче

Задача: найти причину падающего теста, исправить реализацию (не `tests/`),
запустить проверку и показать exit code. Критерии: `npm test` проходит,
скрытые проверки значений проходят, `tests/` не изменены, публичный API цел,
изменён только `src/pricing/discounts.mjs`.

Варианты:

- **A — raw**: только встроенные инструменты; 13 Laya-инструментов отключены
  через `--disallowedTools`. Проверено по `tool_usage`: Laya-вызовов нет.
- **B — self-fetching без Laya**: Laya-сервер остановлен; используются
  `laya_search`/`laya_read_relevant`/`laya_run_check`, но ранжирование
  детерминированное (по пересечению слов).
- **C — self-fetching с Laya**: сервер запущен; те же инструменты, Laya
  ранжирует кандидатов.

По три прогона на вариант, один и тот же prompt, одинаковый стартовый коммит.

### Вклад

- **A → B (детерминированный отбор, без Laya):** input −26.5%, total −26.4%,
  wall −24.5%, запросов −37.5%, tool calls −35%. Это вклад дедупликации,
  ограничения выдачи, `laya_run_check` и постраничного `laya_get_chunk`;
  Laya-инференс здесь не участвует.
- **B → C (вклад Laya):** input −9.3%, total −9.2%, запросов −10%, tool calls
  −23%, wall +1.3% (в пределах разброса). Laya в этих прогонах участвовала
  только в ранжировании `laya_search`; `laya_read_relevant` на маленьких
  блоках возвращал `laya_used=false`, `laya_run_check` Laya не использует.
- **A → C:** input −33.3%, total −33.2%, wall −23.5%, запросов −44%,
  tool calls −50%.

**Осторожно с выводом:** n=3 на одной задаче; диапазоны B и C пересекаются
(B: 244–266 тыс., C: 208–268 тыс.). Снижение ~9% — наблюдаемый эффект на этом
наборе, а не статистически доказанная величина. Основной выигрыш даёт
детерминированный self-fetching, а не Laya.

### Дочитывания и потерянные фрагменты

- A: 4–9 `Read`, без дублей; 20–22 tool calls.
- B: 1–3 `Read` + 2–6 `laya_read_relevant`; в B4 один `laya_get_chunk`.
- C: 1–2 `Read` + 2 `laya_read_relevant`; в C5 два `laya_get_chunk`.
- Потерь важных фрагментов не было: все 9 прогонов прошли скрытую приёмку,
  тесты не менялись, правился только нужный модуль.

### Задержка и стоимость Laya отдельно

- `laya_search` в C: 409–488 мс на вызов; из них Laya-ранжирование ≈187 мс
  (C3), остальное — `rg` и запуск процесса.
- `laya_health`: 14–37 мс (это `/info`, не классификация).
- `laya_read_relevant`: 30–50 мс; на малых блоках Laya не вызывается
  (`laya_used=false`).
- `laya_run_check`: 1.3–2.7 с, но это в основном `npm test`, не Laya.
- Суммарная локальная задержка Laya на задачу — менее 1 с; разница wall между
  B и C (~1 с) в пределах шума.

## 3. Доставка DoneGate агенту

Сессия `sess_4bf5cb18-941d-4a5a-ab8c-27bf68353bbb` (новая, после изменения
файла и без запуска тестов) получила уведомление и **процитировала его
дословно**:

> Laya DoneGate: изменены файлы кода (1), проверка «test» не запускалась.
> Запусти laya_run_check("test") и покажи exit code. Это уведомление, не блокировка.

В другой сессии (`sess_8b688d8d-67cf-45db-ac17-e6bc37b6839f`) агент после
уведомления действительно вызвал `laya_run_check("test")` и показал exit 1
(фикстура была намеренно сломана). В metrics: `done_gate notify`, затем после
проверки — `done_gate log/no-gaps`, то есть evidence обновился.

Механизм: уведомление отдаётся с `continue:true` и `stopReason`, один раз на
сессию (`done_notify`); `decision:"block"` не используется. Без `continue`
Stop завершал ход, и `additionalContext` не попадал в следующий запрос модели.

## 4. Постраничный `laya_get_chunk`

Добавлены `offset`, `limit` (по умолчанию 4000 символов, максимум 50000),
`has_more`, `next_offset`; `full=true` явно возвращает весь текст. Полный текст
по-прежнему хранится на диске. Проверено тестом на файле >20 КБ: страница
ограничена, `has_more=true`, `full=true` совпадает с исходником побайтно.

## 5. `exit:3` в MCP-проверке

Это **синтетическая намеренно падающая проверка** в E2E-фикстуре:
`check.mjs` печатает `INTENTIONAL_FAILURE: exit 3` и делает `process.exit(3)`.
Она существует, чтобы проверить, что `laya_run_check` не скрывает провал и
сохраняет полный вывод в chunk. Это не штатная проверка проекта.

Реальные прогоны A/B/C после исправления дали `npm test` exit **0**.
Промежуточный `exit 1` в DoneGate-тесте — ожидаемый: там специально не
исправляли баг, а проверяли, что уведомление заставит агента запустить тесты.

## 6. Ограничения

- Один фикстур-проект и n=3 на вариант; для строгой статистики нужен больший
  набор задач и прогонов.
- Модель CLI — локальная `Kibborg_Flash_v5.7`; это не `deepseek-flash` текущей
  desktop-сессии. Внутри A/B/C модель одинаковая.
- A/B/C используют одинаковые plugin hooks; различаются только доступные
  Laya-инструменты и состояние Laya-сервера.
- Usage взят из провайдера (`input/output/cache_read`), без оценки
  `bytes/2.8`. Байты выдачи инструментов измеряются отдельно.
- Laya-вклад ~9% медианного input на этой задаче не отделён от стохастичности
  выбора запросов моделью; это наблюдаемый эффект, не доказанная константа.
- Wall-time включает локальную модель, инициализацию MCP и один тестовый
  прогон; на другой машине числа будут другими.
