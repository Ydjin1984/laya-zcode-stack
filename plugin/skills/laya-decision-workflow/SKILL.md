# Laya: рабочий процесс без искусственных вызовов

Laya — локальный decision-engine (`127.0.0.1:8095`, модель ~322M). Она не
генерирует код и не рассуждает: отвечает на **типизированные вопросы** о
коротком тексте (`choice`, `score`, `noul`) за десятки миллисекунд. Ценность —
в дешёвом отборе до того, как текст попадёт в контекст основной модели.

**Нет обязательного `laya_*` вызова на ход.** Если задача решается одним
точным чтением или короткой командой — решай её напрямую. Laya — инструмент,
а не ритуал.

## Что вызывать

| Ситуация | Инструмент | Почему |
|---|---|---|
| Нужно найти что-то в проекте, попаданий много | `laya_search(query, root, budget)` | сам выполняет rg/обход, дедуплицирует и ранжирует; агенту не нужно передавать вывод в MCP |
| Нужен фрагмент большого файла вокруг совпадений | `laya_read_relevant(path, query, budget)` | сам читает файл, даёт блоки с контекстом, отмечает пропуски, полный файл — в chunk |
| Нужно проверить изменение фактом | `laya_run_check(check_id, budget)` | запускает настроенную проверку, сохраняет полный вывод, возвращает exit code/ошибки/chunk_id |
| Уже есть hits и нужен только порядок | `laya_search_relevant` | совместимость; для нового поиска предпочитай `laya_search` |
| Большой лог/вывод уже получен | `laya_log_triage` | уникальные ошибки с «×N», file:line и подсказками Read |
| Много независимых решений | `laya_batch` / `laya_decide` с несколькими вопросами | один round-trip вместо N |
| Diff >3 ханков | `laya_rank_diff` | порядок внимания; **это не code review** |
| Проверка доступности | `laya_health` | на старте, после сбоя связи или при диагностике — не на каждом ходе |

**Мелкие операции — напрямую.** Файл влезает в одно чтение, поиск даёт
десяток точных попаданий, команда печатает несколько строк — обычный
`Read`/`rg` дешевле, чем лишний round-trip.

## Self-fetching инструменты: как не потерять источник

`laya_search` и `laya_read_relevant` возвращают **выдержки**, а не весь
артефакт. У каждой выдержки есть `chunk_id`:

- полный результат поиска — `laya_get_chunk("<search-…-all>")`;
- конкретный фрагмент — `laya_get_chunk("<search-…-hit-…>")`;
- полный файл — `laya_get_chunk("<file-…>")`;
- полный stdout/stderr проверки — `laya_get_chunk("<check-…>")`.

По умолчанию `laya_get_chunk` отдаёт **страницу** (4000 символов) и поля
`has_more`/`next_offset`; продолжай с `offset`, а весь источник запрашивай
явно `full=true`. Полный текст всегда остаётся на диске.

Вытеснение ≠ удаление. Если в выдержке есть маркер «строки … пропущены» —
это не ошибка инструмента, а бюджет; перед правкой или выводом о поведении
дочитай нужный участок (chunk или `Read(offset, limit)`).

## Бюджет Laya: max_len ≠ head_max_len

- `max_len` — **вся** последовательность `[CLS] head [SEP] options [SEP] state [SEP]`.
- `head_max_len` — только сторона вопроса: инструкция + все варианты ответа.
- Свободное место под `state` = `max_len` минус head/options и служебные токены.
  Поэтому длинные `criteria` у choice/score уменьшают место под state, а число
  символов ничего не говорит о числе токенов.

Перед `/decide` клиент вызывает `/count` с **той же полной постановкой вопроса**.
Если state не помещается, он сокращается с явным маркером и повторным замером;
если не помещается сам вопрос (инструкция обрезана или варианты схлопнулись) —
`/decide` не вызывается, возвращается ошибка с числами. Не полагайся на
«≤1400 символов»: это только жёсткий предохранитель.

**Вероятность не равна точности.** `answer_confidence` — калиброванная
уверенность модели в ответе, а не доказательство факта. Доменные факты
проверяй по коду, `git status`, exit code и тестам.

## Как формулировать вопросы

1. Один вопрос — одно решение.
2. Все независимые вопросы — в один `laya_decide`/`laya_batch`.
3. Критерии — короткие описания по 3–10 слов; до ~20 вариантов.
4. Язык инструкции — язык текста (русский state → русская инструкция).
5. Важные факты — в начало state: при нехватке бюджета режется хвост.
6. Порог — по `answer_confidence`, не по `confidence` (энтропия).
7. Смотри `warnings`/`fit`: `state_dropped`, `head_truncated`, `collapsed`,
   `truncated_by_client` означают, что ответ неполон. Укороти вход или
   упрости вопрос.

## Контекст и доказательства

- **Требования пользователя, актуальные ошибки, принятые решения и
  доказательства проверок не вытесняются** без возможности восстановления.
  `laya_context_pick` всегда оставляет pinned-виды; остальное доступно через
  `laya_get_chunk`.
- `laya_run_check` — единственный правильный способ получить факт проверки:
  он возвращает `exit_code`, `success`, ошибки, итог и chunk. Провал или
  таймаут видны в тексте и структуре; не пересказывай их как успех.
- `laya_rank_diff` только упорядочивает ханки. Полноценный code review —
  отдельная работа: читай изменённый код и проверяй последствия.
- При сомнении **дочитывай оригинал**, а не достраивай по сниппету.

## Границы доверия и лимиты

- Низкий риск/высокая релевантность Laya никогда не расширяют разрешения и не
  заменяют проверку.
- При недоступности Laya инструменты возвращают детерминированную часть и
  `degraded: true`; продолжай работу штатно.
- Сервис по умолчанию работает с бюджетом `max_len=1024`; после одного
  forward-pass на ~8 тыс. токенов инстанс может перейти в медленный режим до
  перезапуска (`<repo>\engine\stop-laya.cmd` → `start-laya.cmd`).
- Один вызов `/health` — это не скорость классификации: health меряет `/info`,
  а `/decide` включает инференс. Не смешивай эти числа в отчётах.

## Диагностика

- `/laya-status` — режимы, чекпоинт, метрики.
- `/laya-bench` — латентность `/decide`/`/benchmark`.
- `laya_health` — доступность и чекпоинт.
- `node scripts/laya-admin.mjs doctor` — самодиагностика интеграции.

## Отчёт об использовании

Если инструменты реально применялись, в финале укажи: какие вызовы были,
что они заменили, сколько текста не попало в контекст (по фактическим
размерам) и какие ограничения остались. Если не применялись — одной строкой
скажи это; не выдумывай нулевую экономию и не вызывай Laya ради отчёта.
